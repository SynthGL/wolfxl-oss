## Reproduction and interpretation

- Machine: MacBook Pro, Apple M5 Pro, 18 CPU cores, 64 GB RAM, arm64.
  Runtime platform: macOS 26.5.1. Date in the filename is the local run
  date; the UTC completion timestamp above is the following day.
- Installed artifacts: PyPI `wolfxl==2.0.8` and `openpyxl==3.1.5`,
  not the working-tree package. No local build or skip-build path was used.
  WolfXL's published binary is a release-wheel build; compiler flags are
  not embedded in its distribution metadata. Source release `v2.0.8`
  resolves to `396be5a9f5bb82c2892c9236e3571515315c4bfb`.
- Measured WolfXL native-extension SHA-256:
  `4037c754609f3af49fdb4d736923a3087a71edd81062fd5e9e3f781df293ebbf`.
  openpyxl `__init__.py` SHA-256:
  `b36b17729f138575c7b3035287e52e422e411eca1ab2e7335328cd373d15ba97`.
- Unchanged committed harness SHA-256:
  `b452bb84a16489bbf1828358cc3f4f9808bfa63cbc767af9b6bca6fed4d08bf9`.
  The dirty-tree marker reflects documentation and regression work performed
  during the run, not a locally modified benchmark or measured package.
- Five measured iterations for every timing, including large cases.
  Small cases discard one warmup; large cases discard none. Imports are
  outside timing. OS filesystem caches are not flushed; this is an
  in-process workload comparison, not a cold-start or cold-disk benchmark.
  Large samples include the initial invocation in the same process;
  raw individual samples remain separate in the JSON.
- Overall command timeout: 3,600 seconds. There is no per-case timeout in
  this committed harness. No cases failed, timed out, or were skipped.
  Peak-RSS results are single fresh-subprocess observations, not medians
  of five. They are not used in the speed headline.
- Raw artifact: [`2026-10-02-community-2.0.8-vs-openpyxl-3.1.5.json`](2026-10-02-community-2.0.8-vs-openpyxl-3.1.5.json),
  written at the timestamp above, SHA-256
  `e4a6295a789b34cd495a74b22927820699f5c211ccb382e900aa3d5a0dda9472`.
- Read/write headline: **3.0-17.3x faster than openpyxl on the committed
  read/write benchmark (small-file gains vary)**, rounded to one decimal.
  All read/write comparison rows
  below qualify, including cell-by-cell and styled cases; no edit phase is
  mixed in. The endpoints are `read_styled_cells` (3.0040x) and
  `write_multi_sheet_plain` / `wolfxl_write_rows_fast_multi_sheet` (17.2698x).
  Bulk APIs differ from openpyxl's per-row/per-cell API shape.
- End-to-end edit ratios are 2.4-2.7x. The higher edit-only phase ratios
  exclude setup and openpyxl verification and are not headline read/write
  speedups. These are product-workload measurements on this configuration,
  not universal speed guarantees.
- This range is not a claim about other benchmark suites. The separate
  [officelibs small-feature snapshot](https://officelibs.com/excel/)
  reports WolfXL read/write totals of 13.9/11.3 ms versus openpyxl
  24.0/27.6 ms, roughly 1.7/2.4x. Those results demonstrate why the
  headline must be scoped to this committed harness.
- Workload caveat: `plain_row()` emits at most five populated columns.
  Large plain cases are configured as 200,000 x 8, but actually populate
  200,000 x 5 (one million cells). Nominal `units` and `units_per_second`
  retain the harness output unchanged; do not present them as actual
  populated-cell throughput. The comparison still gives both engines the
  same input. Historical 1.6-million-cell claims do not describe this run.

```bash
uv venv .bench --python 3.13
uv pip install --python .bench/bin/python wolfxl==2.0.8 openpyxl==3.1.5
.bench/bin/python benchmarks/benchmark_openpyxl_vs_wolfxl.py \
  --rounds 5 --large-rounds 5 --output-dir benchmarks/results \
  --prefix 2026-10-02-community-2.0.8-vs-openpyxl-3.1.5
```
